# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Blockwerk Orange** — a small, extensible CMS written in dependency-free PHP 8 (no Composer, no framework) with a MySQL/MariaDB backend, a vanilla-JS drag-and-drop content editor and a built-in **AI assistant**. The product name appears in the admin shell, login/install screens, installer and docs; the backend design and logo use orange tones. UI language is German — keep all user-facing strings (admin UI, flash messages, seed content) in German.

The AI assistant talks to a central service run by the vendor; every installation needs its own licence key (`bw-…`) with a token balance, bought at <https://blockwerk-orange.de/ki-guthaben>. The service itself is not part of this repository.

## Running

No build step, no package manager, no test suite (yet). Local dev server:

```bash
php -S localhost:8000 -t public public/index.php
```

Requires a local MySQL/MariaDB. On first request the install wizard (`/install`) creates the schema, seed data, and writes `config/config.php` (gitignored — its absence means "not installed", which redirects everything to `/install`). `install.php` at the repo root is a separate standalone bootstrapper (upload one file → it downloads and extracts the CMS zip, then hands over to the wizard); it is not part of the app runtime.

Syntax check: `php -l <file>` and `node --check <file>` for the JS assets. There is no linter config.

## Architecture

Front controller `public/index.php` autoloads classes by namespace path (`Core\App` → `app/Core/App.php`), loads `app/helpers.php` (global helpers: `e()`, `url()`, `abs_url()`, `redirect()`, `flash()`, `csrf_*()`, `slugify()`, `format_date_de()`), then runs `Core\App`.

- **`Core\App`** — resolves the base URL (handles both docroot=`public/` and root-`.htaccess`-rewrite setups), enforces the installed/not-installed redirect, runs the schema self-migration, starts the session, runs a global CSRF check on every POST (`_csrf` field or `X-CSRF-Token` header), and registers all routes. Routes map to `[ControllerClass::class, 'method']`; the site catch-alls (`/news/{slug}`, `/events/{slug}`, `/{slug}`) must stay registered last. `App::isHttps()`/`scheme()` honour `X-Forwarded-Proto` so absolute URLs stay correct behind a TLS proxy.
- **Controllers** (`app/Controllers/`) — admin controllers extend `Admin\AdminController` (constructor enforces login; `view()` wraps content in the `admin/_shell` sidebar layout). News and Events share `Admin\PostControllerBase` (one `posts` table with a `type` enum). Models (`app/Models/`) are thin static PDO wrappers over `Core\Database::pdo()`.
- **Rendering pipeline** (`Core\Renderer`) — a page = layout HTML (from DB) with placeholders replaced: `{{content}}`, `{{title}}`, `{{site_name}}`, `{{logo}}`, `{{base_url}}`, `{{year}}`, `{{menu}}`, `{{languages}}` and `{{template:key}}` (recursive, depth-capped). `{{logo}}` renders the site logo (`Setting site_logo`) as `<img class="site-logo">` and stays empty when none is set — that makes a logo work in **any** layout, classic HTML included (the seed layout and `Themes::html()` ship the placeholder in their brand link, `BlockRegistry::lBrand()` and `Shop::invoiceLogo()` fall back to the same setting, and `.site-logo` is styled in `cms-blocks.css` so it applies everywhere). The renderer also **auto-injects** `cms-blocks.css`/`cms-blocks.js` plus a `<style>` block with the layout's design (colors/fonts as CSS variables `--cms-primary`, `--cms-font-body`, …) and `<link>`s for locally stored fonts. News/event detail pages (`Renderer::renderPost`) use the first layout.
- **Design system** — each layout has a JSON `design` column (colors from color pickers + font ids), edited in the layout form. Block "Designvorlagen" (variants) render as `cms-v-<variant>` classes; their styles in `public/assets/css/cms-blocks.css` consume the CSS variables, so variants automatically follow the layout colors. `FontController` downloads Google Fonts (css2 + woff2) into `public/uploads/fonts/<slug>/` and rewrites the CSS to local paths (GDPR-friendly self-hosting).
- **Themes / design tokens** (`Core\Themes`, admin "Designs") — a theme is a whole-look preset: colors + `headerBg`/`headerText` + a **token set** (`radius`, `button` round/pill/sharp, `hero` vh, `container`, `section` padding, `shadow`, `scale`, `headingWeight`/`headingSpacing`/`uppercase`/`headingFont` bar/center). `Themes::css()` emits these as `:root` CSS variables (`--cms-radius`, `--cms-hero-h`, `--cms-btn-radius`, `--cms-section-space`, `--cms-shadow`, `--cms-font-scale`, `--cms-heading-*`) which `cms-blocks.css` consumes everywhere, so a theme restyles the whole site (not just colors). Applying a theme overwrites the default layout's HTML + `design.css`. Custom designs (incl. AI-built via the `create_design` tool) live in the `themes` table and use the same token structure. The hero block uses `--cms-hero-h` when its own height is 0 (auto). Colored rows (`.cms-section`) support a slant/wave top/bottom edge (`row.style.st`/`sb` = `slant`/`wave`, clip-path/SVG-mask in the section's own color) and a per-row corner radius (`row.style.radius`); blocks with a background default to `--cms-radius`.
- **Blocks are registered in two places** — server-side rendering in `Core\BlockRegistry` and editor definition (label, defaults, inspector fields, optional `items` list spec) in `blockDefs` in `public/assets/js/editor.js`. A new block type requires both; `BlockRegistry::types()` is also the server-side whitelist used by `PageController::sanitizeContent()`. Block data may contain scalars plus one level of item lists (arrays of objects with scalar values — see `sanitizeBlockData()`); anything deeper is stripped on save.
- **Editor** (`public/assets/js/editor.js`, view `admin/pages/editor.php`) — holds the content JSON (`rows[] → columns[] (span 1–12) → blocks[]`, plus optional `css` string and per-row `style`) as client state and saves via `POST /admin/pages/{id}/content` with the CSRF token in a header. Drag & drop covers three cases via a single `dragData` variable (`{kind:'new'|'move'|'row'|'new-row'|'col', …}`): block-palette items (`kind:'new'`) and existing blocks (`kind:'move'`, dragstart on `.ed-block`) drop into any column's `.ed-blocks` zone (`bindDropzone`); the top toolbar's row/column-layout presets (`kind:'new-row'`) and existing rows (`kind:'row'`, dragstart on `.ed-row-label`) drop onto the thin `.ed-row-insert` strips between rows or directly onto a row (`bindRowDropzone`, before/after by cursor Y); columns reorder within their own row only (`kind:'col'`, dragstart on the `.ed-col-handle` ⠿ in `.ed-col-bar`, dropped via `bindColDropzone`, before/after by cursor X, guarded to `dragData.from.r === r`). The canvas is **WYSIWYG**: block HTML comes from `POST /admin/preview/blocks` (`PreviewController`, same `BlockRegistry::render` as the frontend), batched and cached client-side, debounced on edits. The editor page loads `cms-blocks.css` + the layout's `designHead()`; frontend CSS is written with `:where(body)` zero-specificity selectors so admin styles win outside the canvas. Per-block graphical settings live in `data._style` (margins, padding, align, colors, radius → inline-style wrapper `div.cms-block`, see `BlockRegistry::styleAttr()`); per-row settings in `row.style` (full-width background section `div.cms-section`, paddings). Initial state comes from a `<script type="application/json">` tag (encoded with `JSON_HEX_TAG`). Shared admin widgets (media picker modal, rich text editor) live in `public/assets/js/admin-tools.js` (`window.AdminTools`), used by both the editor and the news/event forms; `window.CMS_BASE` is set in `admin/_shell`.
- **AI assistant** — `Core\Ai` (client for the vendor service, licence key + token balance in settings; `Ai::buyUrl()` returns `Setting ai_buy_url` or the default purchase page), `Core\AiSchema` (system prompt with the full block catalog + live site context, Anthropic tool definitions), `Core\CmsAgent` (the agent itself: `plan()` proposes a checklist, `run()` executes one step in a tool loop of at most 16 rounds), `Admin\AiController` (HTTP layer + transcript). Tools cover create/update/get for pages, layouts, posts (news/events), global blocks and templates, plus `set_logo` (works on every layout — writes `Setting site_logo` and, on classic layouts, injects `{{logo}}` into the brand link/header), `set_layout_html` (replaces a classic layout's HTML; guarded: builder layouts rejected, `{{content}}` required exactly once), `set_layout_design`, `create_design`, `generate_image`, `download_image`, `fetch_url`, `list_media` and `load_font` (Google Fonts via `FontController::download`). Content is validated through the same `BlockRegistry::sanitizeTree` as the editor; after create_page/update_page `CmsAgent::pageChecks()` reports images without `alt` and missing Impressum/Datenschutz pages back to the model. The prompt enforces: build a **complete** site even when the request names only a detail, mandatory Impressum + Datenschutz pages, accessibility (alt texts, one `h1`, contrast ≥ 4.5:1), a real hero image, and a self-review pass.
- **Media** — uploads go to `public/uploads/` (gitignored), validated by finfo MIME against a whitelist; `GET /admin/media/list` serves the JSON for the picker.
- **Shop** (optional, off by default) — tables `shop_categories`, `shop_products`, `shop_shipping`, `shop_orders`, `shop_order_items`. Prices are stored in **cents (int)**; `Core\Shop` centralises settings (enabled flag, root page, currency, payment toggles, PayPal creds) plus `formatPrice`/`parsePrice`/`url`. `Core\Cart` is a session cart keyed by product id. Admin under `/admin/shop/*` (products, categories, orders, settings incl. shipping methods; nav group "Shop"). The storefront is served by `Controllers\ShopController`, rendered through the site layout via `Renderer::renderRaw()` (views in `app/Views/shop/`). Frontend routes are registered in `App::registerRoutes` **only when the shop is enabled**, under the slug of the chosen root page (`/{slug}`, `/{slug}/kategorie/{s}`, `/{slug}/produkt/{s}`, `/{slug}/warenkorb`, `/{slug}/kasse`, `/{slug}/bestellung/{token}`, `/{slug}/paypal/*`) — registered before the `/{slug}` catch-all. Payment: invoice + prepayment complete the order directly; PayPal uses the JS SDK buttons with server-side create/capture (`Core\PayPal`, Orders v2). Invoices are generated as PDFs by `Core\InvoicePdf` (`Core\Pdf` primitives, no library). Shop frontend styles live in `cms-blocks.css`.
- **Updates** — `Core\Updater` downloads the package zip (default: GitHub main archive, overridable via `Setting update_zip_url`/`update_version_url`), extracts it over the installation while never touching `config/` and `public/uploads/`, then re-runs `createSchema()`. Version = `VERSION` file at repo root, checked against the raw `VERSION` URL. Admin UI at `/admin/update` (incl. backup download/restore). For a private source repository a GitHub token can be stored in `Setting update_token`: `zipUrl()`/`versionUrl()` then switch to the API endpoints and `Updater::authHeaders()` adds the `Authorization` header — only for github.com hosts, never for third-party URLs.

Views are plain PHP templates under `app/Views/`, rendered via `Core\View::render($template, $data, $shell)`. Always escape output with `e()`; block/layout/template HTML from the DB is intentionally rendered raw (admin-authored).

## Conventions

- Schema changes go into `Core\Database::createSchema()` (uses `CREATE TABLE IF NOT EXISTS`; new columns via `Database::ensureColumn()` in `migrate()` — there is no migration system). `App::ensureSchema()` runs both automatically whenever `Setting schema_version` differs from `VERSION`.
- Redirect-after-POST with `flash('success'|'error', msg)` for all admin form actions.
- All URLs in PHP go through `url()` / `redirect()` / `abs_url()` so subdirectory installs keep working; never hardcode absolute paths.
- Seed data (default layout, main-menu template, example pages incl. Impressum/Datenschutz) lives in `InstallController::seed()`.
- **Every released change bumps `VERSION` (semver) and gets an entry in `CHANGELOG.md`** — the in-app updater compares against `VERSION` and users read the changelog to see what changed.
- Frontend block structure/styles belong in `cms-blocks.css` (auto-injected everywhere); `site.css` is only the default layout's theme (header/menu/footer) and both consume the `--cms-*` variables with fallbacks.
